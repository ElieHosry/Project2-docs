GovTech

Scope

Institutional service platforms — for the public sector and private institutions alike (city services, universities, hospitals, companies). The shape that matters: a citizen/customer/member-facing side plus a staff/operations side, connected by service workflows, live data feeds and dashboards, with accountability (roles and audit trails) as the signature requirement. A campus attendance system belongs here as much as a city permit office.

Examples

  1. Queue management for public services — simulates and tracks citizen queues (license office, clinic); real-time dashboard; service-flow editor. References:

    • Qminder for healthcare
    • Qmatic queue system demo (YouTube)

  2. Facility booking & occupancy management — members book rooms/labs/desks; live occupancy from presence signals; staff ops side with floor-plan view; booking rules engine in C++. (Replaced "City resource dashboard", which moved to Visualization & Analytics, July 2026.) References:

    • Skedda — space booking & occupancy (official)
    • Robin — workplace management (official)

  3. Digital form & permit workflow — citizens submit applications, officers process them; data-driven form builder as the custom tool; Firebase auth for roles. References:

    • Cloudpermit building permitting
    • Typeform form builder

  4. Public transport tracker — simulated bus/train positions processed in a C++ feed engine; live 2D map with arrival predictions; route/timetable editor. References:

    • Transit app
    • Citymapper overview (YouTube)

  5. Citizen issue reporting (311-style) — citizens photo-report potholes and broken lights; staff triage dashboard; category workflows; public transparency stats. References:

    • SeeClickFix
    • Reporting an issue on SeeClickFix (YouTube)
    • FixMyStreet

How each requirement applies

Common to all five: C++ Performant Service (feed/queue/workflow engine) · Application Communication (UI ↔︎ engine) · Continuous Integration · Front-end + Back-end · Data-Driven Architecture (services, forms, routes as data) · Authentication ✅ (citizen/staff roles are central).

1. Queue management

Platform fit: Main: Web browser on mobile + Native PC (staff ops) — web browser on mobile for citizens (take a ticket), PC dashboard on the staff side. Extended: Firebase + Linux server set up by M2 (full use in T2). Device: Pixel 9a.
Front end: Citizen ticket page (web), staff queue dashboard. Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES); Native — Kotlin + C++ (Android Studio, OpenGL ES).
Back end: Queue dynamics simulation, wait-time statistics, notifications, Firebase records. Languages: C++.
Backend scope: Server-indicated — server set up by M2, full use in T2.
  • Loop and/or service: simulates citizen arrivals, service times, and queue dynamics in real time — a true simulation.
  • Data-driven: forms, workflows, rules and thresholds defined as hot-reloadable data.
  • Custom tool (adapted): service-flow editor (counters, services, priorities). 2D (adapted): live queue dashboard rendering.
  • External DB / Analytics ⏭️: tickets, wait-time statistics; auth for staff vs. citizen roles.

2. Facility booking & occupancy management

Platform fit: Main: Native mobile + Native PC (staff ops) — members book and check in from their phones (reference device); the floor-plan ops view stays on the PC side. Extended: Firebase + Linux server set up by M2 (full use in T2). Device: Pixel 9a.
Front end: Member booking app, live floor-plan occupancy view, staff dashboard. Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES); Native — Kotlin + C++ (Android Studio, OpenGL ES).
Back end: Booking rules engine, occupancy/presence event processing, schedule import, Firebase sync & notifications. Languages: C++.
Backend scope: Server-indicated — server set up by M2, full use in T2.
  • Loop and/or service: live occupancy state — presence events and booking transitions processed continuously; a usage simulator drives development.
  • Data-driven: forms, workflows, rules and thresholds defined as hot-reloadable data.
  • 2D: floor-plan rendering with live occupancy coloring. Custom tool (adapted): room/rules/schedule configuration editor.
  • External DB: bookings, occupancy history. Auth: member vs staff vs admin roles. Analytics ⏭️: utilization statistics.

3. Digital form & permit workflow

Platform fit: Main: Web browser on mobile (citizens apply) + Native PC (officer ops) (officers review) — a natural two-front-end split. Extended: Firebase + Linux server set up by M2 (full use in T2). Device: Pixel 9a.
Front end: Citizen forms rendered from JSON schemas, officer review UI. Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES); Native — Kotlin + C++ (Android Studio, OpenGL ES).
Back end: Workflow/state machine engine, validation engine, RBAC & audit, Firebase. Languages: C++.

  • Custom tool: the data-driven form builder applies directly and is the strongest deliverable here.
  • External DB / Analytics ⏭️: applications, statuses, processing-time metrics; auth central (citizen/officer roles).

1. Queue management for public services

M1:

  • M1G1 ⭐ Application Shell, Real-time C++ Simulation Loop, Input & Core Logic
    Tech & dependencies
    • Tech: SDL2/3/ImGui shell, fixed-timestep loop simulating citizen arrivals and service times; CMake, Git.
    • Prerequisites: None — foundation of this project.
    • Feeds into: M1G4 (queue engine runs on its tick); every other goal.
  • M1G2 ⭐ Data-Driven Architecture of Core Objects / Entity System
    Tech & dependencies
    • Tech: Counters, services, priorities, and ticket types defined as JSON entities (nlohmann/json) with hot-reload.
    • Prerequisites: M1G1 (shell and loop to host the entity system).
    • Feeds into: M1G4 (engine consumes service definitions); M2G2 (service-flow editor edits this data).
  • M1G3 ⭐ Debugging, Profiling, Stress Test & CI
    Tech & dependencies
    • Tech: ImGui overlay of live queue state, Tracy profiling, Catch2 stress tests flooding the queue with thousands of simulated citizens, GitHub Actions Windows/Linux builds.
    • Prerequisites: M1G1 (running loop to instrument).
    • Feeds into: M2G3 (CI hardening); validates M1G4 under load.
  • M1G4 Real-time Feed / Queue Engine
    Tech & dependencies
    • Tech: C++ producer/consumer threads generating ticket events (issue, call, serve, no-show) through a lock-free ring buffer, with CSV replay of past office days.
    • Prerequisites: M1G1 (simulation tick); M1G2 (service and counter definitions).
    • Feeds into: M1G11 (event stream for statistics), M1G12 (ticket-called triggers), M2G4 and M2G10.
  • M1G11 Statistics & Wait-Time Analytics
    Tech & dependencies
    • Tech: Per-service/per-counter wait and service-time aggregation in C++, custom SDL2/3/OpenGL charts (no chart libs), history persisted to Firestore.
    • Prerequisites: M1G4 (ticket event stream); M1G2 (event data model).
    • Feeds into: M2G10 (historical calibration for predictions); M2G4 (dashboard heatmaps and history).
  • M1G12 Notification System
    Tech & dependencies
    • Tech: Firebase Cloud Messaging push for "your ticket is called", in-app event bus for the staff dashboard, service worker on the citizen web ticket page.
    • Prerequisites: M1G4 (queue events to notify on); Firebase project with citizen/staff Auth.
    • Feeds into: Citizen ticket experience at showcase; M2G10 (pushing predicted wait times).

M2:

  • M2G1 ⭐ Architecture — Optimization & Platform Validation
    Tech & dependencies
    • Tech: Tracy profiling of the queue engine under thousands of concurrent tickets, ASan/UBSan, memory pools and threading tuning, Emscripten validation of the citizen web page.
    • Prerequisites: All M1 goals (hardens the M1 queue codebase).
    • Feeds into: M2G4 (dashboard frame budget) and M2G10 (prediction throughput).
  • M2G2 ⭐ Content Editor — Core
    Tech & dependencies
    • Tech: Service-flow editor in C++/ImGui — configure counters, services, and priority rules with JSON round-trip and an undo/redo command stack.
    • Libraries/Software: Dear ImGui, nlohmann/json
    • Prerequisites: M1G2 (service/counter data model it edits).
    • Feeds into: M1G4 (engine runs edited flows live); M2G4 (dashboard reflects reconfigured offices).
  • M2G3 ⭐ CI — CMake, Code Quality, Build Standards & Packaging
    Tech & dependencies
    • Tech: CMake presets, clang-format/clang-tidy gates, CPack packaging of the staff dashboard plus Emscripten citizen web build in the Actions matrix.
    • Prerequisites: M1G3 (CI and test foundation).
    • Feeds into: Release builds of every goal for the showcase.
  • M2G4 Dashboard — Advanced
    Tech & dependencies
    • Tech: Supervisor dashboard with live queue layers per counter, wait-time heatmaps, and scrubbing through the day's queue history (SDL2/3/OpenGL + ImGui).
    • Prerequisites: M1G4 (live events) and M1G11 (aggregates/history); M2G1 (rendering budget).
    • Feeds into: Staff-side showcase; M2G7 gates its supervisor-only views.
  • M2G7 RBAC & Audit Logging
    Tech & dependencies
    • Tech: Firebase Auth custom claims for counter staff vs. supervisor, permission checks in the C++ service, append-only audit log of every ticket action (call, skip, transfer, close).
    • Prerequisites: M1G4 (ticket actions to log); M1G11/M2G12 (Firebase records and identity in place).
    • Feeds into: M2G4 (role-gated dashboard panels); trust story of the whole product.
  • M2G10 Prediction Engine (wait times)
    Tech & dependencies
    • Tech: Exponential smoothing / simple Kalman filtering over queue lengths and service rates, calibrated per service against M1 wait-time history.
    • Prerequisites: M1G4 (live queue state) and M1G11 (historical statistics).
    • Feeds into: Citizen ticket page ETAs, M1G12 (predicted-wait notifications), M2G4 (forecast panel).

  • M1G17 Presence & Signal Detection Engine
    Tech & dependencies
    • Tech: Occupancy sensing via the pool's detection goal — ultrasonic chirp or BLE RSSI processing in custom C++ producing room-level presence events with confidence.
